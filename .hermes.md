# Violin project contract

This file is loaded by Hermes from the repository root. Runtime behavior and
tool schemas remain authoritative when this summary and the code differ.

## Safety boundary

- Work only against targets covered by written authorization and the approved
  `$ENG_DIR/scope/scope.yaml`.
- Complete the scoping workflow before target interaction.
- Ask before actions that affect availability, integrity, credentials,
  sensitive data, persistence, stealth, or third-party systems.
- Never fabricate, rewrite, or delete evidence to improve a result.
- Follow `skills/pentest/references/standards.md` for evidence and approval
  rules.

## Required state

Do not touch a target until these files exist and pass bootstrap validation:

- `$ENG_DIR/scope/scope.yaml`
- `$ENG_DIR/state/ptt.md`
- `$ENG_DIR/state/history.md`
- `$ENG_DIR/hypotheses.md`
- `$ENG_DIR/state/checkpoint.json`

Use the administrative CLI to initialize or inspect an engagement:

```bash
python scripts/violin_guard.py init-engagement "$ENG_DIR" --host example.com
python scripts/violin_guard.py check-bootstrap --eng-dir "$ENG_DIR"
python scripts/violin_guard.py validate-scope --scope "$ENG_DIR/scope/scope.yaml"
python scripts/violin_guard.py status --eng-dir "$ENG_DIR"
```

The CLI `check-command` subcommand is diagnostic only. Target commands must use
the plugin tools.

## Execution contract

- Use `violin_exec` for one target command and `violin_exec_burst` for a
  bounded command file.
- Use `terminal` only for host-local preparation and administration.
- Maintain exactly one active `[~]` PTT task under the command's phase.
- Existing PTT tasks cannot be moved to another phase. Start or create a task
  under the required phase.
- Record hypotheses with `violin_record_hypothesis`.
- Review each completed batch once with `violin_review_batch`.
- If a pending batch belongs to the wrong task, use
  `violin_rebind_pending_batch` only after explicit confirmation.
- At a heartbeat gate: call `violin_status`, review any pending batch, then call
  `violin_heartbeat_done`.

`violin_exec` has no binary allowlist. Tool availability, permissions, root,
GUI, service, hardware, and interactive-TTY requirements remain host concerns.

The raw-terminal hook can block obvious target literals, but it is not network
containment and must not be treated as scope enforcement.

## Skill binding

Load `skills/pentest/SKILL.md` as the orchestrator. For an active task, call
`violin_record_ptt` with its routed `skill`, concrete `technique`, and any
required hypothesis. A first call may return `skill_prepared` without changing
the PTT. Repeat the same transition after skill delivery to bind the receipt.

Use `violin_status` when binding is blocked. Do not create
`.skill-loaded-*` files; marker files do not prove delivery.

## `execute_code`

Prefer typed execution for target work. When local Python automation is
required, the first line must contain the audit metadata expected by the
runtime:

```python
# violin: {"eng_dir":"<path>","phase":"<phase>","target":"<target>","session_id":"<session-id>"}
```

Violin saves the submitted source under `$ENG_DIR/evidence/<phase>/` and
records its digest and status. Audit metadata does not provide the containment
of `violin_exec`.

## Evidence and state

- Store raw output under `$ENG_DIR/evidence/<phase>/`.
- Keep tokens, secrets, dumps, and proof output out of `$ENG_DIR/state/`.
- Capture HTTP status, headers, and body for decisive web evidence.
- Cite exact evidence files, not directories.
- A validated hypothesis needs reproducible proof and a canonical
  `evidence/findings/FIND-NNN.md` record.
- The executor writes command history. Do not recreate history manually.

## Session continuity

Continue in the current conversation after `/goal set` or context compression.
Re-read `$ENG_DIR/state/checkpoint.json`, `$ENG_DIR/state/ptt.md`, and
`$ENG_DIR/state/phase-summary.md`, then call `violin_status`. Do not infer
tested state from memory or start over.

Global Hermes memory and unrelated chat history are not engagement evidence.
Do not carry targets, credentials, scope assumptions, or findings between
projects.

## Interaction modes

In interactive work, announce the next bounded batch and ask when authorization
or scope is unclear. Summarize a completed batch in three to five bullets with
the evidence path and next action.

In non-interactive benchmark mode, do not call `clarify` or wait for an
acknowledgment. Safety, scope, evidence, and guard rules still apply.

## Tool environment

Kali and Parrot are the expected native environments. Other supported layouts
include Docker Kali through `scripts/kali.sh`, WSL, PowerShell, Git Bash, and
approved remote jump hosts. Check `command -v <tool>` before relying on a tool.
If it is missing, use an installed equivalent or ask before installation.

Target-facing background work must use `violin_exec(background=true)`. Do not
start target jobs through raw `terminal`.

## Forbidden behavior

- Out-of-scope testing
- Credential attacks without explicit authorization
- Social engineering unless explicitly scoped
- Persistence, malware, destructive activity, or anti-forensics
- Unnecessary access to or export of sensitive data
- Silent omission of required coverage because a tool is unavailable

Detailed phase and routing instructions live in `skills/pentest/SKILL.md`.
