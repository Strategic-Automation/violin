Supervised agentic pentesting that produces proof, not prose.

Violin is built for working testers on authorised engagements. It drives the tools already in your image through a single guarded execution boundary, returns a signed receipt for every command, and refuses a finding that cannot cite one. You keep the engagement state, the coverage disposition, and the final call.

Before a target command runs

One boundary — violin_exec. Fail closed.

  1. Written authorisation in scope.yaml
  2. Approved-scope match for the resolved target
  3. Active PTT task under the current phase
  4. Routed specialist skill bound to the task
  5. Hypothesis binding for the command
  6. Command history and synchronisation state
  7. Engagement gates — any failure denies
A passing command returns a signed execution receipt. violin_submit_finding will not accept a finding without one.

Built for the way engagements actually run

Not a demo agent that finds one bug in a deliberately vulnerable app. A harness for scoped, multi-day client work where the report has to survive scrutiny.

Scope checked per command

Every target-touching command is resolved against the approved scope before it starts. Out-of-scope hosts are denied, not logged-and-run. Path-scoped URL exclusions are honoured.

Your tools, your image

No tool-specific adapters and no target allowlists: installed non-interactive tooling (nmap, nuclei, ffuf, sqlmap, curl) runs through one boundary, so what you learned in the last engagement still applies.

Coverage you can defend

A coverage matrix derived from scope obligations plus methodology disposition gates means every in-scope route and required testing category ends with a disposition — not with silence.

Evidence for the report

Findings carry severity, summary, and the signed receipts that authenticate the decisive request and response bytes — the artefact you need at readout, not a screenshot you have to re-earn.

Survives a multi-day engagement

PTT tasks, hypotheses, checkpoints, command history, and evidence live in engagement state on disk. Context compression does not reset the assessment; you resume from the checkpoint.

Human-in-the-loop by design

Bounded command bursts are reviewed and settled after execution, pending batches can be rebound, and phase transitions require an active task under that phase. The agent proposes; the guard disposes.

Use it for

  • Scoped web, API, identity, business-logic, and LLM-security testing
  • Consultants who need per-finding evidence and a defensible coverage story
  • Teams that want agent leverage without losing the chain of custody
  • Authorised lab, CTF-style, and internal assessment work

Do not use it for

  • Anything without written authorisation and an approved scope
  • Unattended mass scanning of hosts you do not own
  • Replacing your judgement on severity, impact, or client context
  • Network isolation — that is your environment's job, not the profile's

How it works

Violin does not ask you to trust the model. It asks the guard to answer three questions on every command.

Is it in scope?

Scope, phase, active PTT task, routed skill, hypothesis binding, and command history are validated before execution. Gates fail closed: a malformed scope denies the command rather than guessing.

Can you prove it?

Each passing execution issues a signed receipt covering the command and its decisive response bytes. violin_submit_finding binds the finding to those receipts.

Can you resume it?

State is written to the engagement directory as the work happens, so an interrupted or compressed session continues from evidence rather than from re-exploration.

Stated plainly: the guard is an execution-boundary control, not network containment. The raw-terminal hook is a best-effort safety net. Run Violin in an environment you control, only against systems you own or are written-authorised to test.

How the approaches differ

Agentic pentesting tools differ less in what they can find and more in what they can answer afterwards. This compares design centres, not named products or measured results.

A checklist you can apply to any tool — including this one — is the point of the evaluation discussion.

What an engagement looks like

One active task, one routed skill, one guarded command boundary, receipts as you go.

  1. Scope first

    Bootstrap the engagement and approve scope/scope.yaml. Nothing touches the target before this exists, and the coverage matrix is generated from its obligations.

  2. Activate exactly one task

    Create and start a PTT task under the current phase, naming the routed skill and the concrete technique. Work does not begin a new phase without a task under it.

  3. Run guarded commands

    Recon through the same boundary as exploitation. A typical recon command through the tool:

    // one guarded command, resolved against the approved scope
violin_exec(
  eng_dir  = "engagements/acme-web",
  phase    = "RECON",
  target   = "app.example.com",
  command  = "nmap -sV -sC -T4 app.example.com -oA quick_app",
  label    = "service-discovery"
)
// gates passed → status: ok, signed execution receipt written
  4. Keep hypotheses honest

    Hypotheses carry status, confidence, a cheapest test, and kill criteria. Evidence changes their status; a hypothesis that survives without evidence does not become a finding.

  5. Review the batch

    Bounded bursts are reviewed and settled so state reflects what actually ran, including partial output and failures.

  6. Submit findings that cite receipts

    Severity, summary, and the decisive evidence. One vulnerability per submission, with the receipts that authenticate the request and response that proved it.

  7. Close out coverage, then report

    In-scope routes and required testing categories get a disposition — tested, negative evidence, or an explicit exclusion with a reason. Then the report, then the retrospective.

Honest limits

Most tool pages skip this. The project's own documentation does not, so neither does this one.

A single run is a noisy sample

Agentic runs vary run to run. Violin reports a distribution — mean pass@1, pass@k, pass^k — and prefers the mean to the best run. A repo test pass is not a live benchmark score.

The guard is not containment

It constrains what the agent is allowed to run against an approved scope. It does not isolate the network for you.

No model choices baked in

Violin adds no credentials and selects no provider; it uses your Hermes configuration. Use a capable model — weaker models produce weaker hypotheses, not safer ones.

Receipts are not judgement

They prove what was sent and received. Severity, impact, exploitability, and whether a finding belongs in the report remain human calls.

Questions testers actually ask

Does this replace Burp, nmap, or nuclei?

No. It gates and drives the non-interactive tooling already installed in your environment, and keeps the evidence and coverage record. Interactive tooling and your own judgement stay where they are.

Can it wander out of scope?

The guard denies commands whose resolved target is not in the approved scope, and honouring path-scoped URL exclusions is part of the gates. The raw-terminal hook is a best-effort net rather than containment, so run Violin inside an environment you control.

Which model should I use?

Whatever your Hermes configuration provides. Violin selects no model and ships no credentials. The README suggests a capable default if you are starting from nothing.

Can I run it on a live client engagement?

With written authorisation and an approved scope, like any other tooling. You own approvals, target ownership, data handling, and local law. Violin is for authorised assessment only.

How does a finding get accepted?

violin_submit_finding binds the finding to signed receipts that authenticate the decisive request and response bytes. A claim without receipts is a hypothesis, not a finding.

What does it cost?

Nothing. MIT licensed, no hosted service, no per-target fees, no Violin account.

Where are the benchmark numbers?

In the methodology, not in a headline. The project publishes how scoring works and explicitly warns against quoting a single run; see docs/BENCHMARKS.md.

How do I ask for a playbook that does not exist?

Open an idea in Discussions: name the capability and the obligation a good entry would enforce. Generic capabilities become playbooks; specific targets do not.

Quick start

Requirements: Hermes Agent 0.18.0+, a Kali Linux or Parrot OS tool environment, Python 3.11 and uv for local development, and written authorisation with an approved scope.

$ hermes profile install https://github.com/Strategic-Automation/violin
$ hermes -p violin

# then, in the session:
Run an authorized penetration test against example.com.

Violin collects scope before any target interaction. Read the engagement lifecycle, the benchmark methodology, and the security policy before your first run.
